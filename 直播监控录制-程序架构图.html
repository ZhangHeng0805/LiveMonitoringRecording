LiveMonitoringRecording · 程序架构图

多平台（抖音 / B站 / 快手）直播间监控 · 自动录制 · 弹幕字幕 · 本地可视化控制台 —— 单进程、多直播间、单机部署的 Java 桌面/后台常驻程序

JDK 1.8 构建 Maven 多模块 + shade 单 jar 入口 FileModeMain（目录批处理） / Main（命令行） 形态 托盘常驻 + 本地 HTTP 控制台 外部进程 Chromium(Playwright) · ffmpeg · cpolar

一、分层架构 自上而下：入口 → 调度 → 取数 → 采集 → 服务 → 基础设施

L0
入口 / 启动层
授权校验 + 监听来源解析 + 服务注册
FileModeMain 当前运行
目录批处理入口：扫描 ./room/*.room.json，逐房间提交监听任务；并发上限 maxMonitorThreads；全部结束即 System.exit。
cn.zhangheng.lmr.FileModeMain
Main / ApplicationMain
命令行入口：交互输入或参数 [房间ID] [是否录制] [平台]；单房间、支持循环监听；RunMode=TASK。
lmr.Main · record.service.ApplicationMain
授权与配置前置
ActivationUtil 校验设备指纹 + xxxr-activation.lic；ConfigKit 读 xxxr.setting，失败即退出。
record.activation · common.setting
服务注册器
ServerStarterManager 统一编排 Starter：本地 API 服务、cpolar 隧道，支持延迟启动与整体停止。
lmr.service
每个 .room.json → 一条监听线程（线程 × 房间）
L1
调度与监听层
状态机 + 轮询 + 生命周期回调，业务主干
MonitorMain（抽象）
单房间监听的编排者：托盘图标、状态机 READY→RUNNING→ERROR→END、循环监听、onStart/onChange/onProgress/onStop 回调。
DouYinMain · BiliMain · KuaiShouMain
RoomMonitor（抽象）
监听心跳：Task 线程池内死循环，按 delayIntervalSec(30s) 调 refresh；开播后 onProgress 汇报；注册 JMX MBean。
DouYinRoomMonitor 等
RoomService（抽象）
平台取数抽象：refresh(force) + 弹幕开关；子类决定走浏览器、HTTP 还是本地解析。
DouYinRoomService · BilibiliService · KuaiShouService
Room 领域模型
直播间状态载体：昵称、是否开播、streams（清晰度→FLV 地址）、观众/点赞/礼物计数、封面、Cookie。
DouYinRoom · BiliRoom · KuaiShouRoom · RoomJson
refresh：拉取直播间实时数据 / 换取 FLV 流地址
L2
数据获取层
浏览器模拟 + HTTP 双通道，Cookie/UA 池
DouYinDataService / DouYinDataHandler
抖音取数主路径：先取 dataUrl，再 getData(force)；分「未开播走浏览器」「已开播走接口」两段。
douyin.service · douyin.browser.factory
Playwright 浏览器封装
浏览器池与页面上下文：PlaywrightBrowserFactory / MyBrowser / BrowserContent；上下文定时清理、异常解析、可无头。
browser-utils · DouYinBrowserFactory · DouyinPlaywright
OkHttp 客户端
全局单例 + 连接池（共 10 空闲、300s）；统一超时、Cookie、UA、短链解析；常驻调度线程避免频繁建线程。
OkHttpFactory · OkHttpUtil · HttpUtils
B站 / 快手取数
B站走接口 + 登录态 Cookie；快手从页面 InitialState 提取直播信息，均不依赖长驻浏览器。
BilibiliService · KuaiShouService · InitialStateExtractor
开播 / streams 就绪 → 触发录制与弹幕；未开播 → 继续轮询
L3
采集与产出层
录制落盘 / 转码 / 弹幕持久化 / 字幕生成
RecorderTask → AsyncTaskQueue
录制调度：优先级队列 + 重试 + 指标统计；异常按 tryRecordSec 退避重录，支持 JMX 观测。

Recorder（抽象）两实现
FlvStreamRecorder：Java 直连 FLV 拉流写文件（无 ffmpeg 依赖）；FFmpegFlvRecorder：子进程录制，可读进度。

弹幕链路
DouYinWebcast → DouYinWebSocket（protobuf 解码）→ MessageListener：聊天/进场/礼物/点赞/关注/统计。
douyin-fetcher · DouyinLiveDecoder

douyin.subtitle · record.util

统计表生成 MonitorDataTableGenerate、直播间封面/短链解析、快捷键触发 ShortcutExecutor。
douyin.util · record.util

三、核心运行链路 六条主干流程

1冷启动与激活

进程起来到开始监听之间的必经路径

xxxr.setting→ ActivationUtil
设备ID + lic→ FileModeMain
扫描 ./room→ ServerStarterManager
API + cpolar→ 每房间一条监听线程

2开播探测（30s 心跳）

整个系统的主动作，决定什么时候开始干活

RoomMonitor
sleep 30s→ RoomService
refresh(force)→ 取 dataUrl
浏览器/接口→ getData
更新 Room→ 未开播继续 / 开播切态→ 托盘 + 息知通知

3自动录制与收尾

开播回调里的一次性长任务，结束即闭环

onChange(LIVING)→ RecorderTask
入优先级队列→ Flv 拉流 / FFmpeg 子进程→ .flv 落盘
超 15G 或切清晰度分段→ FlvToMp4 转码→ 源文件进回收站 + 重新监听

4弹幕与字幕

只在抖音开播期间启动，独立于录制

startSubtitle()→ DouYinWebcast
WS 长连接→ protobuf 解码→ MessageListener
分类回调→ chatLog / subtitleLog
异步批量写→ 下播后 AssGenerator 出 ASS

5控制面：网页改监听

不重启进程就能增删启停直播间

前端 index.html→ /api 查计数→ /action
CheckUtils 鉴权→ addMain / restartMain / delMain→ 写 .room.json + 提交线程池

6文件面：看录制回放

大文件拖拽必须靠 Range，否则会整包读

/fileRes?key=&path=→ 目录分页
FilePageUtils→ Range 解析
206 + Content-Range→ RandomAccessFile
8K 分块流式→ 浏览器播放器 / 下载

五、业务判断与风险点 从代码里读出来的结构性问题

强依赖第三方页面与 Cookie
抖音取数走真实 Chromium，登录态过期即整条链路失效；浏览器进程（~69MB）不随 Java 退出而必然回收，需关注僵尸 node/chromium。
单进程多房间 = 线程 × 房间
每个房间一条监听线程 + 一条录制任务 + 弹幕 WS + 异步日志线程；房间数上去后线程与句柄线性增长，受 maxMonitorThreads 约束。
双 Task 体系并存
record.bean.Task（业务执行池）与 common.task.Task（队列任务）语义不同、生命周期不同，改动时容易改错一侧。
录制与监听是两条独立闭环
录制异常靠 onProgress 里重新入队恢复；监听靠 MonitorMain 的 do-while + 退避重试恢复。二者没有统一事务，可能出现「在录但已判下播」的短窗。
对外暴露靠 cpolar，鉴权只有设备密钥
控制面鉴权是设备 ID/Cookie 级，不是账号体系；隧道公网可达时，安全边界实际由这层薄鉴权撑着。
文件面性能取决于 Range 正确性
录制文件是大体积 MP4/FLV，拖拽体验完全依赖 206 分片与秒级 304 判断；这两处已在本轮修复，但仍建议对并发下载做限速/连接数约束。
结构依据仓库源码（live-common / live-monitor-record / 三个平台模块 / browser-utils / douyin-fetcher / common-libs / cpolar-tool）实际类与调用关系整理；端口、线程数、缓存参数均取自当前 xxxr.setting 与常量定义。
